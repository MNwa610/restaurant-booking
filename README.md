# Система бронирования столиков

Система бронирования столиков ресторана на Python с веб-интерфейсом на Django.

## 1. Назначение проекта

Учебное приложение для учёта столиков ресторана и управления бронированиями.
Проект позволяет хранить сведения о столиках, пользователях и бронированиях,
выполнять основные операции с этими объектами и предоставлять доступ
к информации через веб-интерфейс Django.

Проект развивается поэтапно: консольная версия приложения дополняется
веб-интерфейсом и постепенно переводится на возможности Django.

Приложение позволяет:

* просматривать столики в браузере;
* просматривать информацию о конкретном столике;
* просматривать список бронирований в браузере;
* просматривать информацию о конкретном бронировании;
* проверять доступность столика на текущую дату;
* искать столики по расположению;
* проверять вместимость столиков;
* создавать бронирования;
* отменять бронирования;
* хранить данные между запусками приложения.

## 3. Предметная область

В системе используются три основные сущности:

* Столик (`Table`) – номер, вместимость и расположение;
* Пользователь (`User`) – идентификатор и сведения о пользователе;
* Бронирование (`Booking`) – идентификатор, столик, пользователь,
  дата бронирования и состояние бронирования.

Для предметной области сохранены собственные Python-классы в `models/`.
На ПР9 те же сущности описаны моделями Django ORM в приложениях
`tables` и `bookings`. JSON и `data/restaurant_booking.sqlite` не удалены.

Пользователь может создавать бронирования столиков на определённые даты.
Один столик не может иметь два активных бронирования на одну и ту же дату.
Отменённое бронирование не блокирует столик.

## 5. Веб-интерфейс

Веб-часть приложения реализована на Django.

Основные страницы:

* `/` – главная страница;
* `/tables/` – список столиков;
* `/tables/available/` – поиск свободных столиков на выбранную дату;
* `/tables/<int:table_number>/` – информация об отдельном столике;
* `/bookings/` – список бронирований;
* `/bookings/statistics/` – статистика бронирований;
* `/bookings/<int:booking_id>/` – информация об отдельном бронировании.

Для формирования страниц используются Django-шаблоны.
Генерация HTML непосредственно в Python-коде веб-представлений не используется.
Функция `page()` больше не используется веб-представлениями.
Представления подготавливают данные и передают их в шаблоны через контекст.

Если столик или бронирование не найдены, ответ возвращается со статусом 404.
Для неизвестного URL настроена собственная страница ошибки (`handler404`).

## 6. Django Template Language

Шаблоны используют возможности Django Template Language.

### Базовый шаблон

Общий шаблон страниц: `templates/base.html`.

Он содержит общую HTML-структуру страницы, подключение стилей и JavaScript,
навигацию и блоки для содержимого отдельных страниц.

Дочерние шаблоны используют наследование:

```django
{% extends "base.html" %}
```

Содержимое страниц размещается в блоке `{% block content %}`.
Заголовок страницы задаётся через блок `{% block title %}`.

### Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные шаблоны:

* карточка столика: `tables/includes/table_card.html`;
* статус бронирования: `bookings/includes/booking_status.html`;
* навигация: `includes/navigation.html`.

Подключение выполняется с помощью `{% include %}`.

### Контекст

Представления передают данные в шаблоны через словарь контекста.
Например, для списка столиков:

```python
context = {
    "tables": tables_list,
}
```

В шаблоне данные доступны по имени переменной:

```django
{% for table in tables %}
```

Для страницы отдельного столика используется переменная `{{ table }}`.
Аналогичный подход используется для бронирований.

### Циклы и условия

Для формирования списков используются циклы `{% for %}`.
При отсутствии элементов используется `{% empty %}`.
Условия используются для отображения различного содержимого страницы
и состояния бронирования:

```django
{% if booking.is_cancelled %}
```

## 7. Фильтры шаблонов

В шаблонах используются стандартные фильтры Django Template Language.

Количество столиков:

```django
{{ tables|length }}
```

Значение по умолчанию:

```django
{{ table.location|default:"Не указано" }}
```

Фильтры используются для представления данных и не содержат бизнес-логику.
Дата бронирования на текущем этапе хранится как строковое значение
и выводится без преобразования средствами шаблона.

## 8. URL-маршрутизация

Для страниц используются именованные маршруты Django и пространства имён:

* `homepage:index`;
* `tables:list`, `tables:available`, `tables:detail`;
* `bookings:bookings`, `bookings:statistics`, `bookings:detail`.

Примеры ссылок:

```django
{% url 'tables:list' %}
{% url 'tables:detail' table.number %}
{% url 'bookings:bookings' %}
{% url 'bookings:detail' booking.id %}
```

Ссылки в шаблонах формируются через `{% url %}`, а не за счёт жёстко заданных адресов.

## 9. Статические файлы

Статические файлы проекта находятся в каталоге:

Используются:

* `css/style.css`;

## 10. Хранение данных

JSON-хранилище предыдущих практических работ сохраняется:

* `data/tables.json`;
* `data/users.json`;
* `data/bookings.json`.

Загрузка JSON выполняется средствами модуля `storage.py`.
Предметные объекты создаются на основе собственных Python-классов из каталога
`models/`.

На ПР7 данные перенесены в базу SQLite `data/restaurant_booking.sqlite`.
Таблицы создаются скриптом `sql/schema.sql`.
Перенос из JSON выполняется скриптом `db/import_json.py`.

`DATABASES` по-прежнему указывает на `db.sqlite3`, а не на файл из `data/`.
Исходная база ПР7 и SQL-скрипты сохранены.

## 17. База данных SQLite

Структура базы данных:

Таблица `tables`:

* `number` INTEGER – номер столика, первичный ключ;
* `capacity` INTEGER – вместимость;
* `location` TEXT – расположение.

Таблица `users`:

* `id` INTEGER – идентификатор, первичный ключ;
* `name` TEXT – имя пользователя;
* `email` TEXT – электронная почта.

Таблица `bookings`:

* `id` INTEGER – идентификатор, первичный ключ;
* `table_number` INTEGER – внешний ключ на `tables.number`;
* `user_id` INTEGER – внешний ключ на `users.id`;
* `booking_date` TEXT – дата бронирования в формате YYYY-MM-DD;
* `is_cancelled` INTEGER – признак отмены (0 – активно, 1 – отменено).

Файл схемы: `sql/schema.sql`.
Модуль подключения: `db/database.py` (`PRAGMA foreign_keys = ON`).
Скрипт импорта: `db/import_json.py`.

SQL-запросы сохранены в `sql/queries.sql` и включают выборку списков,
фильтрацию `WHERE`, соединение таблиц `JOIN`, агрегатные функции,
группировку `GROUP BY` и фильтрацию групп `HAVING`.

На ПР7 Django-представления получали данные из SQLite через модуль `sqlite3`.
На ПР9 те же страницы читают `db.sqlite3` через Django ORM.

Страницы, отображающие данные:

* `/tables/` – список столиков;
* `/tables/<int:table_number>/` – карточка столика;
* `/bookings/` – активные бронирования;
* `/bookings/<int:booking_id>/` – карточка бронирования;
* `/tables/available/` – свободные столики на выбранную дату;
* `/bookings/statistics/` – количество бронирований по столикам.

## 19. ПР9: Django ORM

Веб-интерфейс получает данные через модели Django, а не через `sqlite3.connect()`.

### Модели и связи

* `tables.Table` — первичный ключ `number`, вместимость, расположение.
* `bookings.User` — имя и email пользователя ресторана
  (это не `django.contrib.auth.User`).
* `bookings.Booking` — дата, признак отмены,
  `ForeignKey` на столик и пользователя.
* Абстрактная модель `TimeStampedModel` добавляет `created_at` и `updated_at`.

Связи:

* `Booking.table` → `Table`, `on_delete=PROTECT`, `related_name="bookings"`;
* `Booking.user` → `User`, `on_delete=PROTECT`, `related_name="bookings"`.

`PROTECT` выбран, чтобы нельзя было удалить столик или пользователя,
пока на них ссылаются бронирования. Обратные связи:
`table.bookings.all()` и `user.bookings.all()`.

### Какая база используется

* Django: `db.sqlite3` (`DATABASES` не менялся).
* Источник переноса: `data/restaurant_booking.sqlite`.
* Каталоги `sql/`, `db/`, `data/` сохранены.

### Как переносились данные

1. `python db/inspect_source_db.py` — просмотр исходных таблиц.
2. `python manage.py migrate` — создание таблиц ORM.
3. `python db/import_sqlite_to_orm.py` — независимые сущности
   (`Table`, `User`), затем `Booking`; `transaction.atomic()`;
   `update_or_create(pk=...)`; `date.fromisoformat` и `bool(...)`.

После импорта количество записей совпадает с источником:
5 столиков, 2 пользователя, 3 бронирования.

### Что изменено относительно методички Roomly

Проект — бронирование столиков ресторана, а не комнат Roomly.
Поэтому модели называются `Table` / `User` / `Booking`,
фильтр списка — `table`, а не `room`, URL остались `/tables/` и `/bookings/`.

## 20. Дальнейшее развитие

Следующие этапы предполагают формы Django и операции создания,
изменения и отмены бронирований через веб-интерфейс.

* создание бронирования;
* отмена бронирования;
* создание пользователя.
